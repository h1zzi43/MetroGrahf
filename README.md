# MetroGrahf — планировщик маршрутов в метро

## Что решает проект

Консольное приложение на C#, которое по заданной схеме метро (граф станций и перегонов
с временем в пути) находит:

1. **Кратчайший по времени маршрут** между двумя станциями.
2. **Маршрут с минимальным числом перегонов** (пересадок), если время в пути не важно.

Пользователь вводит Id станции отправления и Id станции назначения, программа
печатает путь, суммарное время и число перегонов.

## Использованные структуры данных и алгоритмы

| Компонент | Что применено | Зачем |
|---|---|---|
| `MetroGraph` | **Список смежности** (`Dictionary<string, List<Edge>>`) | Хранение графа |
| `Dijkstra` | **Алгоритм Дейкстры** + `PriorityQueue<TElement,TPriority>` (двоичная куча) | Кратчайший по времени маршрут |
| `BfsMinTransfers` | **BFS** + `Queue<T>` | Маршрут с минимумом перегонов |
| Восстановление пути | `LinkedList<T>` + `Dictionary` предков | Сборка пути от финиша к старту |
| Сравнение Id | `StringComparer.OrdinalIgnoreCase` | Ввод в любом регистре |

### Сложность

| Алгоритм | Время | Память |
|---|---|---|
| Dijkstra (куча) | `O((V + E) log V)` | `O(V + E)` |
| BFS | `O(V + E)` | `O(V)` |

где `V` — число станций, `E` — число перегонов (рёбер). Так как перегоны
двунаправленные, в списке смежности хранится `2·E` записей.

## Обоснование архитектурных решений (выделенный раздел)

### 1. Список смежности vs матрица смежности

**Выбран список смежности.**

- Схема метро — **разреженный граф**: каждая станция соединена в среднем
  с 2–4 соседями. Матрица смежности размера `V × V` для 200 станций — это
  40 000 ячеек, из которых заполнено меньше 1 %. Это неоправданный расход памяти.
- Список смежности занимает `O(V + E)` памяти и даёт перебор соседей за `O(deg(v))`,
  а не за `O(V)`, как матрица.
- Единственное преимущество матрицы — проверка «есть ли ребро между u и v» за `O(1)`.
  В нашей задаче такая проверка не нужна: мы всегда идём по всем соседям.
- **Вывод:** для разреженного графа метро список смежности строго лучше по памяти
  и не хуже по времени на операциях, которые мы реально выполняем.

### 2. Дейкстра vs BFS для «кратчайшего по времени»

**Выбран Дейкстра.**

- Граф **взвешенный**: у каждого перегона своё время в минутах.
- BFS находит кратчайший путь **по числу рёбер**, но не по сумме весов.
  Контрпример: `A→B` = 1 мин, `A→C→B` = 2 + 2 = 4 мин. BFS выберет `A→C→B`,
  потому что там 2 ребра, но Дейкстра правильно выберет `A→B` (1 мин).
- Дейкстра корректен, потому что все веса **положительные** (время перегона > 0).
  При отрицательных весах нужен алгоритм Беллмана–Форда, но таких данных
  в задаче не бывает по определению.

### 3. PriorityQueue vs линейный поиск минимума

**Выбрана `PriorityQueue` (двоичная куча).**

- Наивная реализация Дейкстры ищет минимум в массиве `dist` за `O(V)` на каждом шаге —
  итого `O(V² + E)`. При `V = 200` это 40 000 операций, что ещё терпимо, но плохо
  масштабируется.
- С кучей каждая операция `ExtractMin`/`Insert` — `O(log V)`, итого
  `O((V + E) log V)`. При больших графах это ощутимо быстрее.
- `PriorityQueue<TElement,TPriority>` — стандартный класс .NET, реализация
  двоичной кучи; писать свою кучу не нужно.

### 4. Регистронезависимые словари (`StringComparer.OrdinalIgnoreCase`)

- Пользователь может ввести `r1` вместо `R1`. Если словари регистрозависимы,
  `ContainsStation("r1")` вернёт `false`, и алгоритм скажет «маршрут не найден»,
  хотя станция есть.
- Решение **на уровне модели данных**, а не UI: граф сам по себе умеет искать
  Id без учёта регистра. Это архитектурно правильнее, чем нормализовать ввод
  в `Program.cs` — любой другой клиент графа (например, будущий REST-сервис)
  автоматически получит то же поведение.

## Альтернативные подходы, которые рассматривались и были отклонены

| Альтернатива | Почему отклонена |
|---|---|
| **Матрица смежности** | Разреженный граф → неоправданный `O(V²)` по памяти. |
| **BFS для кратчайшего по времени** | Не работает на взвешенных графах (см. контрпример выше). |
| **Беллман–Форд** | Избыточен: все веса положительные, Дейкстра быстрее. |
| **A\*** | Нужна эвристика (например, географические координаты станций), которой у нас нет. Для произвольного графа A\* вырождается в Дейкстру. |
| **Floyd–Warshall** | Считает расстояния между **всеми** парами за `O(V³)`. У нас запрос — одна пара, `O(V³)` неоправдан. |
| **Своя реализация кучи** | `PriorityQueue` из .NET уже реализует двоичную кучу корректно и эффективно. |
| **Нормализация ввода в UI** | Лечит симптом, а не причину: граф остался бы регистрозависимым. |

```
MetroGrahf/
├── MetroGrahf.csproj
├── Program.cs              — точка входа, интерактивный режим и режим --test
├── Models/
│   ├── Station.cs          — модель станции
│   ├── Edge.cs             — модель перегона
│   └── RouteResult.cs      — результат поиска маршрута
├── Graph/
│   └── MetroGraph.cs       — граф на списке смежности
├── Algorithms/
│   ├── Dijkstra.cs         — кратчайший по времени
│   └── BfsMinTransfers.cs  — минимум перегонов
├── Demo/
│   └── DemoData.cs         — тестовая схема метро
├── Tests/
│   └── TestRunner.cs       — самописные тесты
└── README.md
```

## Как запускать

```bash
# интерактивный режим
dotnet run

# тесты (основной сценарий + пограничные случаи)
dotnet run -- --test
```

### Пример работы

```
=== Планировщик маршрутов в метро ===
Станций в графе: 9

Доступные станции:
  R1 — Северная
  R2 — Центральная
  ...

Введите Id станции отправления: r1
Введите Id станции назначения: b3

--- Кратчайший по времени маршрут (Дейкстра) ---
Путь: R1 -> R2 -> B2 -> B3
Время: 14 мин
Перегонов: 3

--- Маршрут с минимумом перегонов (BFS) ---
Путь: R1 -> R2 -> B2 -> B3
Время: 14 мин
Перегонов: 3
```

## Покрытые тестами случаи

- Основной сценарий: `R1 → B3` (Dijkstra), `R1 → G3` (BFS).
- Регистронезависимый ввод: `r1 → b3`.
- Старт равен финишу.
- Несуществующая станция.
- Пустой граф.
- Несвязный граф (нет маршрута).
- Граф из одной станции.
